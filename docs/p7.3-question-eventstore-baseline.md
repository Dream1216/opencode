# P7.3 Question EventStore Baseline

## Scope

P7.3 converges Question lifecycle decisions on one aggregate contract without
changing the OpenCode agent loop. The first batch adds a pure aggregate and
does not switch production reads or writes.

## Current call paths

The production compatibility path is:

```text
question tool
  -> packages/opencode/src/question/index.ts
  -> EventV2Bridge.publish(question.asked|replied|rejected)
  -> SQLite EventV2
  -> PostgreSQL replication outbox
  -> PostgreSQL EventStore
```

The newer Core path is:

```text
QuestionV2.Service
  -> EventV2.publish(question.v2.asked|replied|rejected)
  -> QuestionPersistence.restore
  -> SQLite aggregate replay
  -> optional PostgreSQL pending recovery
```

HTTP list, reply, and reject currently use the compatibility service.

## Confirmed gaps

1. V1 and V2 event protocols are both durable and have separate restore paths.
2. Pending maps are runtime coordination state, but terminal decisions are not
   guarded by an aggregate-level compare-and-append command.
3. Two processes can both restore the same pending request and attempt a
   terminal append.
4. PostgreSQL restore failures are logged and converted to an empty list, which
   can surface later as `Question request not found`.
5. The Web and CLI observe protocol-specific event names instead of a single
   lifecycle projection contract.
6. Expiration and cancellation are not durable Question terminal states.

## P7.3 aggregate contract

The first aggregate contract reuses the existing durable V2 events:

```text
question.v2.asked@1
  -> question.v2.replied@1
  -> question.v2.rejected@1
```

Legal states are `empty`, `pending`, `answered`, and `rejected`.

Identical command retries are idempotent. Different terminal decisions,
different answers, wrong sessions, invalid answer cardinality, and terminal
events before `asked` are conflicts.

## Next integration batch

P7.3.2 will add a command gateway that reads the aggregate, makes a decision,
and appends with an expected sequence. V1 HTTP and tool entry points will map
through adapters behind a feature flag. The existing pending maps remain only
as in-process wait handles and read-model caches.
