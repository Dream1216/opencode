# P7.4.0 Reproducible Release Source Baseline

## Goal

Bind the deployed OpenCode VibeCode source to a deterministic source manifest and a unique Git commit.
The baseline must be rebuildable from a clean checkout without production credentials or generated
dependencies.

## Source boundary

The manifest includes source files, documentation, lockfiles, migrations, tests, workflows, executable
bits, and symbolic-link targets.

The following generated or host-specific paths are excluded:

- `.git`
- `.cache`
- `.turbo`
- `dist`
- `node_modules`
- `target`
- `.DS_Store`
- `packages/core/compatibility/release-source-baseline.json` to avoid a self-referential digest

## Production comparison

The pre-baseline comparison used the deployed release:

`/www/wwwroot/code.jxhh.com/releases/opencode-v1.18.9-vibecode-p7.3.7-20260730-023928`

Results before committing the baseline:

- production files: 6,498
- local files: 6,499
- production-only files: 0
- local-only files: `packages/core/script/release-source-baseline.ts`
- changed files: `.github/workflows/question-shadow-rollout.yml`

The workflow difference is expected because the protected GitHub Actions workflow was fixed and merged
after the production source archive was created. No other production source drift was detected.

## Credential scan

The release source contains no `.env`, private key, known production password, or production database
URL. High-confidence scanner matches were reviewed:

- PostgreSQL URLs in documentation use `...` placeholders.
- The Bedrock test access key ends in `MPLE` and is an AWS example value.

Production credentials remain outside the release under `/www/wwwroot/code.jxhh.com/.env` and
`/www/wwwroot/code.jxhh.com/secrets`.

## Generate the manifest

```bash
bun run packages/core/script/release-source-baseline.ts \
  --root "$PWD" \
  --output /tmp/release-source-baseline.json
```

Copy the generated manifest to:

`packages/core/compatibility/release-source-baseline.json`

Running the command again must produce the same `treeDigest` because the committed manifest excludes
itself.

## Clean-checkout gate

A release baseline is accepted only when all of the following pass:

1. Frozen dependency installation from the committed lockfile.
2. Core and OpenCode typechecks.
3. Question shadow gate, secret-manager, governed adapter, and base adapter tests.
4. A regenerated clean-checkout manifest matches the committed `treeDigest`.
5. The immutable server release is created from the accepted commit.
6. Local and public health checks return HTTP 200 after cutover.
7. The production build ID and acceptance proof are refreshed to the accepted commit.

## Release identity

The release branch and annotated tag identify the source commit. The committed manifest identifies the
source tree excluding generated dependencies and the manifest itself. The deployment directory must
include the short commit SHA in its name.
