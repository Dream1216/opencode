# P7.7.2.1 Session-scoped legacy Prompt claim

## Incident

The initial production canary exposed an Instance routing gap. PostgreSQL jobs
were partitioned by tenant, but every workspace-local `SessionPrompt` layer
started a generic tenant consumer. A consumer could therefore claim a Session
owned by a different SQLite-backed OpenCode Instance.

The observed job remained `running`, its claim expired repeatedly, and its
attempt counter increased without completing the Prompt generation.

## Fix

- `SessionWorkerQueue.claim(sessionID)` resolves the Session tenant and claims
  only that exact `run_id`.
- The legacy Prompt integration no longer starts a generic consumer in every
  workspace Instance.
- The Prompt request that enqueues a generation consumes only its own Session
  while racing the durable PostgreSQL completion signal.
- PostgreSQL tenant RLS, generation tracking, claim tokens, worker leases, and
  fencing remain authoritative.

## Boundary

This canary deliberately does not scan and recover arbitrary legacy Prompt jobs
after a process restart. Automatic orphan recovery requires an explicit
workspace/directory partition in the durable job contract so a new process can
route a job to the correct SQLite Session projection. That remains a separate
follow-up before broad worker rollout.
