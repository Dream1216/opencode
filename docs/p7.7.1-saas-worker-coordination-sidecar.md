# P7.7.1 SaaS worker coordination sidecar

## Goal

Enable PostgreSQL lease and fencing for selected SaaS tenants without switching
the SQLite-primary OpenCode Session projection to the broader PostgreSQL alpha
backend.

## Runtime contract

The sidecar resolves the tenant from
`opencode_execution_resource_locator(resource_type='session')` for every
Session acquisition and fence assertion.

Production activation requires:

```sh
OPENCODE_DATABASE_BACKEND=sqlite
OPENCODE_SAAS_MODE=true
OPENCODE_POSTGRES_WORKER_COORDINATION_ENABLED=1
OPENCODE_POSTGRES_WORKER_COORDINATION_SAAS_SIDECAR=1
OPENCODE_POSTGRES_WORKER_COORDINATION_TENANTS=tenant_org_canary
OPENCODE_POSTGRES_WORKER_QUEUE_ENABLED=false
```

The allowlist must be non-empty. An allowlisted Session cannot run a model turn
or settle a local tool without a valid PostgreSQL fencing token. Sessions from
other tenants continue through the existing local execution path.

## Deliberate boundary

This phase does not enable the durable queue. Its consumer still owns one static
tenant context. Queue activation requires a tenant-partitioned consumer
registry, bounded tenant discovery, and independent readiness metrics.

## Acceptance

- SQLite remains the primary Session projection.
- A bound canary Session resolves its tenant from PostgreSQL.
- Lease acquisition, heartbeat, completion, and fence validation pass.
- A missing, stale, or cross-Session fence fails closed.
- An unlisted tenant cannot create worker lease rows.
- Production health remains `200` and worker queue remains disabled.
